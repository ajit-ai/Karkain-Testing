## Toolchain environment

- Go 1.27.0 is installed.
- No C compiler is on the default PATH. GCC 14.2.0 exists at
  `C:\msys64\ucrt64\bin\gcc.exe`; `scripts\verify.ps1` adds that directory to
  PATH for the verification session only.
- The default engine is the self-hosted `kcc`, which is built from
  `src/compiler` at run time, so the compiler is invoked with the source
  checkout as the working directory.
- `karkain test` emits non-fatal Winsock linker diagnostics on this host
  (missing `-lws2_32` in the test-binary link step) but still compiles and
  executes tests. Failure detection was verified independently: a
  deliberately failing `assert(false)` produces exit code 4, and a passing
  test that prints a marker produces exit code 0 with the marker visible.

## Language features exercised by this framework

Each item below was exercised through the real v1.2.0 compiler, not inferred
from documentation:

- `func` declarations, untyped parameters, `return`, `let`
- `while` loops and `if` / `else`
- integer and string literals, `+`, `==`, `!=`, `<`, `>`
- arrays: `[]`, `len`, `push`, indexing, mixed element types
- strings: concatenation with `+`, `str(...)`, `contains`, indexing
- `println`, `assert`, `assert_eq`, `assert_ne`
- `public func` exports and sibling-module `import` + qualified calls
  (`import ktesting` / `ktesting.<name>`)
- `karkain check`, `karkain run`, `karkain test` and `--filter`

Important verified semantics:

- Arrays are passed by value. `push(arr, item)` returns a new array; callers
  must capture it (`arr = push(arr, item)`).
- Comparison expressions produce integer `1` / `0` values. Truthiness in
  `assert(...)` and `if (...)` works with those values, but
  `assert_eq(1, true)` fails because the operand types differ. Tests in this
  repository use `assert(cond)` for truthiness instead.

## Verified boundaries / blockers

These are restrictions of the verified baseline, not framework defects:

- **No top-level `struct` declarations** in the stable canonical subset used
  by the compiler; attempts produce parse errors. The framework stores check
  entries as mixed-type arrays instead.
- **`karkain test` does not resolve `import` statements.** Native tests are
  therefore generated by concatenating the real module source with the test
  bodies into one temporary file before running the test driver.
- **Local module resolution is entry-file-directory based**; a module in
  `src/` is not automatically visible to a program in `examples/` or
  `tests/`. The verification script stages the module beside the consumer in
  a temporary directory.
- No claim is made about Linux, macOS, Android, iOS, WASM, GPU, NPU, quantum,
  networking or database support for this framework. None of those surfaces
  are used by Karkain-Testing.

## Scope boundary against the standard library

`std.testing` already supplies hard assertions and boolean-array counting
(`test_expect_*`, `test_pass_count`, `test_fail_count`, `test_all_pass`,
`test_summary`). This framework does not duplicate that API. It adds named,
soft, accumulating checks with per-check diagnostic detail, a report
formatter, and a hard-fail gate, so an entire suite can run to completion and
report every failure in one pass.
